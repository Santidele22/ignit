# PDF Validation Pipeline & Admin Review

Feature: Harden the PDF upload pipeline with a deterministic structural "firewall" (reject active content, encryption, malformed and polyglot PDFs), an optional text-level AI analysis stage (OpenAI-compatible endpoint, e.g. DeepSeek via the gentle-nan proxy), reader response hardening (sandboxed browser viewing), and an admin dashboard to accept/reject uploaded PDFs.
Branch: `feat/pdf-validation-pipeline`

## Specs

- **S1**: PDF Firewall (`backend/src/books/pdf-firewall/` service + helpers) runs inside `POST /books/:id/file` **before** persist, validating every uploaded file in three tiers and **rejecting with HTTP 400** (plus a Spanish message naming the reason) when: Tier 0 — header sanity (`%PDF-1.` within the first 1024 bytes), size cap (existing 50 MB), polyglot signatures before the header (ZIP `PK\x03\x04`, HTML, ELF/Mach-O magic); Tier 1 — lexical scan of the raw bytes with `#XX` hex-name normalization detecting `/JavaScript`, `/JS`, `/OpenAction`, `/AA`, `/Launch`, `/RichMedia`, `/Flash`, `/3D`, `/XFA`, `/EmbeddedFiles`, `/EF`, `/Filespec`, `/SubmitForm`, `/ImportData`, `/Encrypt`; Tier 2 — structural AST traversal via `pdf-lib` (enumerate indirect objects incl. decompressed `/ObjStm`, inspect the catalog and all nested dictionaries/arrays for the forbidden keys), page-count sanity (1..2000, `MAX_FIREWALL_PAGES` env-tunable, protects against PDF bombs), and any parse exception treated as hostile. Encrypted PDFs are rejected outright. Pure decision helpers (forbidden-key sets, hex normalization, verdict assembly) are unit-tested without `pdf-lib` fixtures where possible.
- **S2**: Reader hardening for served PDFs: PDF responses (`GET /books/:id/file` download/stream path) set `Content-Disposition: inline; filename="…"` with `X-Content-Type-Options: nosniff` (verify what exists today; add `Content-Security-Policy: sandbox` scoped to the PDF-serving response or serve PDFs from a sandboxed `<iframe sandbox>` in the reader so the browser's native PDF viewer runs with scripting disabled), and the reader page documents/remains the only rendering path (no external viewer plugins). Keep the existing auth/rate-limit behavior unchanged.
- **S3**: AI text analysis stage (optional, env-gated): after the firewall passes and text extraction completes, if `LLM_BASE_URL` + `LLM_API_KEY` are configured, call an OpenAI-compatible `POST {LLM_BASE_URL}/chat/completions` (`model: LLM_MODEL`, default `deepseek-chat`) with the extracted reading text (truncated to ~24k chars) and a moderation system prompt asking for a strict JSON verdict `{ "safety": "ok" | "suspect", "quality": 1..5, "notes": string }`. Fail-open: on error/timeout (10 s) the analysis records `aiStatus: 'skipped'` and never blocks the upload or the review flow. Results persist on the book row (`aiSafety`, `aiQuality`, `aiNotes`, `aiStatus` columns) and are surfaced in the admin dashboard. Zero external SDK: `fetch` only.
- **S4**: Review workflow on the backend: new `reviewStatus` column on `Book` (`pending` default | `approved` | `rejected`, plus `reviewNote?: string | null`, `reviewedBy?: string | null`, `reviewedAt?: Date | null`); new PDF uploads set/keep `reviewStatus: 'pending'`; admin-only endpoints — `GET /admin/books?review=pending` (paginated list incl. owner email, file size, pages, AI verdict), `POST /admin/books/:id/review` (body `{ decision: 'approved' | 'rejected', note? }`) — guarded with the existing global `RouteRolesGuard` + `@Roles(['admin'])` and `isAdminUser` semantics; approval optionally flips `published` only via an explicit body flag. Owner-visible review state is DEFERRED (L4): the presenter strips moderation columns from owner payloads, so the owner pipeline keeps its current stages until a backend decision exposes review state to owners; `ownerReviewStage()` exists as a tested pure helper for that follow-up. Migration path must match how the backend currently manages schema (`sync-schema.ts`) and never break existing rows.
- **S5**: Admin dashboard (`/admin` route, `web/src/pages/admin.astro` + a Solid component): SSR session check that only renders for `role: 'admin'` users (others get 404/redirect), listing pending books with title/author/owner/pages/size/AI verdict + `Ver PDF` (opens the existing reader or a direct file link in a new tab) and two-step inline `Aceptar` / `Rechazar` (with optional note field, no `window.confirm`), calling the new admin endpoints; after each decision the list refreshes and counts update. Style follows the existing dual-palette tokens; zero new inline scripts (CSP unchanged).
- **S6**: All client interactivity via bundled modules (zero new inline `<script>` tags / CSP hash changes), deterministic Vitest/backend spec coverage for the firewall tiers, verdict assembly, review-status transitions, and AI-stage fail-open behavior; `backend` tests + build and `web` `pnpm test` / `astro check` / `astro build` all pass.
